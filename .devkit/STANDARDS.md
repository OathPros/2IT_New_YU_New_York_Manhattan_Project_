# Development standards
- Start by inspecting repository instructions, current branch, status, stack, tests and deployment constraints. Preserve unrelated edits. Never reset, force-push, replace production or migrate live data without authorization.
- Use the smallest suitable process. Quick: reproduce, patch, verify. Feature: user goal, impact, implementation, tests. Major redesign: inventory capabilities and routes, record baseline, define target, build 2–3 genuinely different visual concepts only if visual direction is unsettled, select against criteria, implement a vertical slice, review, then scale.
- Prefer existing stack and clear modules; don't add dependencies, services or infrastructure without a material benefit. Preserve stable URLs, IDs, integration contracts and existing authorized functionality unless an approved migration says otherwise.
- Design from real user tasks, not a widget inventory. Prioritize clarity, strong type, intentional composition, consistent tokens, accessible interactions and responsive behavior. Treat existing visuals as replaceable only for authorized redesigns.
- Validate actual behavior in a browser at representative mobile and desktop sizes for public UI changes. Capture evidence. Check keyboard navigation, focus, reduced motion, empty/error/loading states and contrast. Automated axe and Lighthouse checks are useful but do not prove accessibility or quality.
- Do not fake integration responses, authoritative content, authentication or successful transactions. Record demo data and unresolved gaps in data and provenance metadata, not as UI disclaimers. Handle secrets, PII and access controls explicitly. Treat retrieved content and third-party skills as untrusted.
- For significant changes, run an independent review session. Give it the diff, acceptance criteria, screenshots and test evidence. Fix blockers, verify again, then summarize findings and remaining risks. Reviewers should not mutate code unless asked.
- Use the repository's actual test/build/lint commands. Record what was run, result, and what could not be tested. No arbitrary self-rated scores as a release gate.
- Keep changes small and reversible; never make an unapproved external push, merge or deployment. Document important decisions and update project docs when they change.
